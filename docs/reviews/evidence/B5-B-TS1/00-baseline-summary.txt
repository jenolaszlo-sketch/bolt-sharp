Every failure had the same shape: IOException wrapping SocketException
(SocketError.ConnectionReset / WSAECONNRESET) raised while the client read the in-flight
terminal FAILURE, before any response bytes were decoded. This is the OS abortive close
retained as OWNER-F01 / Q-B5B-09: the accepted terminal close happens while unread
pipelined tail bytes remain in the server's receive buffer, and the resulting RST can
discard response bytes the client application has not yet copied from the socket.

No baseline failure was a wrong response, an unexpected message, a provider execution or a
hang. The server-side contract was not implicated by these observations; the failing
assertion was the client-visible read itself.

B. Multi-client counter test (unchanged code), 20 fresh isolated processes
--------------------------------------------------------------------------
Filter : FullyQualifiedName~FailureInOneClient_IsolatedFromOthers
Result : 20 passed / 20

The owner closure recorded the original observation: 1 failing execution / 33 full-suite
runs, Expected 1, Actual 0 at MultiClientTests.cs line 78 (see
docs/decisions/B5-B-F01-R1-OWNER-01-owner-closure.md section 8.3). The race is load
sensitive, which is why isolated repetition did not reproduce it. The ordering was
therefore established from the production source rather than from repetition alone:

1. The old test called bad.Dispose(), then Assert.Equal("closed", bad.WaitForClose(5_000)).
   WaitForClose polls the client's own TcpClient with Socket.Poll; after local disposal the
   poll throws ObjectDisposedException and WaitForClose maps every exception to "closed".
   The assertion therefore observed the test's own disposal and provided no synchronization
   with the server.
2. The test then completed a PULL round trip on the good client and immediately asserted
   server.Diagnostics.ConnectionsFailed == 1.
3. ConnectionsFailed is incremented only in BoltTcpConnection.RunAsync's finally block,
   after the handshake failure propagates and session cleanup completes, on the bad
   connection's task. Nothing in the test awaited that task or its diagnostic event. Under
   load the assertion could therefore run before the bad connection's failure accounting,
   observing 0 while the connection had in fact failed.

The correction (see the implementation report) awaits the server's ConnectionFailed and
ConnectionCompleted diagnostic events, which are raised synchronously by the connection task
after the counters are updated, and then asserts exact accounting.
